# git 履歴から非公開リポジトリ名への言及を除去する

## 目的

visibility を public に切り替えると、コミットメッセージと差分の全文がそのまま公開される。すでに tip から削除済みの語であっても、履歴の diff からは完全に復元できる。公開前に履歴そのものから除去する必要がある。

## 現状

- tip (`origin/develop`) の追跡ファイルには該当語の出現が 0 件であることを確認済み (削除はコミット `84901c9` で行われている)
- 一方で `git log --all -S <対象語>` は次の 5 コミットの差分を返す。いずれも履歴に残っており、`git show` で全文が読める
  - `84901c9` (削除そのものを表すコミット。**そのコミットメッセージ自体が対象語を含む**)
  - `c555c77`、`1cd62d7`、`a4ddfa5`、`0047fb1` (削除される前の追加・記述の差分)
- 対象語は GitHub 上で `shiguredo` オーグの公開リポジトリとして検索しても 0 件であり、非公開扱いの語である (`shiguredo-no-secrets` の規約では、プライベートリポジトリ名はリポジトリ名単体・`owner/repo`・URL のいずれも成果物に書かないことが求められる)
- **本 issue には対象語そのものを書かない**。対象語を特定したい場合はコミット `84901c9` のメッセージを参照する (このコミット自体が除去対象に含まれる)
- `develop` と `master` は同一リモートにあり、`master` は `develop` より 168 コミット遅延だが履歴は共有している (`git rev-list --count origin/master..origin/develop` = 168)。両方を対象にしないと除去にならない
- なお `shiguredo-git` の規約では、`git reset` / 履歴を巻き戻しての push はユーザーの明確な指示がない限り禁止されている。本 issue は履歴の**再書き込み**を伴うため、実装着手時にユーザーの明示的な承認が必須である

## 設計方針

次の 2 案のうちどちらを採るか、実装前にユーザーに決めてもらう。

1. **履歴再書き込み**: `git filter-repo` で対象語を含むコミットメッセージと差分を書き換える (または対象語が導入された地点以降を squash する)。既存の公開履歴は失われる。GitHub 上のフォーク・クローン済みキャッシュ、リモートブランチ、`master` も考慮して全ブランチで再実行し、support 経由での古いオブジェクトの GC を依頼する
2. **履歴を縮約して新規公開**: 開発履歴を持たない単一コミット (または数コミット) のリポジトリを新しく作り、`develop` のツリーだけを移植する。内部プロセスの露出を最も減らせるが、既存のコミット履歴・bisect 能力は失う

判断材料:

- 対象語の露出度は「非公開ツール名の単独表記」であり、機密度は高くない。一方コミットメッセージ 143 件超・作者識別子・社内スラッシュコマンド名など、履歴に残る内部情報は対象語以外にもある (`issues/0070` は tip 側の話で、履歴側はカバーしない)
- 案 2 は他の履歴由来の露出をまとめて除去できるが、`master` と既存ブランチの扱いを設計し直す必要がある

どちらの場合も、着手前に次のコマンドで露出範囲を実測して確定させる (実測なしに履歴を書き換えない)。

```
git log --all -S <対象語> --oneline
git log --all -S <対象語> -p
git grep -i <対象語> $(git rev-list --all)
```

## 完了条件

- `git grep -i <対象語> $(git rev-list --all)` が全リポジトリ・全ブランチで 0 件であること
- `git log --all -S <対象語>` が差分上のヒット 0 件であること (コミットメッセージのみのヒットも 0 であること)
- 再書き込み後の履歴で `cargo build` と `cargo test` が通過すること (履歴操作がツリー内容を変えていないことの確認)
- 採用案と、失ったもの (bisect 能力・既存コミットハッシュの参照不能) が本 issue に追記されていること

## 変更対象
