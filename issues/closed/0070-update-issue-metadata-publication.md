## 目的

## 設計方針

1. 追跡されている全 issue ファイルから `Model:` 行を削除する。機械的に消せる行であり、本文の技術的内容に依存しない
2. `Priority:` は **本 issue の対象外とする**。15 ファイルに一貫して入っている歴史的项目であり、公開しても害のない情報 (優先度の高低を示す語のみ) である。閉じた issue の履歴を後から書き換える価値はないと判断する。代わりに「片方だけ残す」状態を避けるため、`Priority` を使う・使わないの方針をどこかに記録する (現行テンプレートに無い = 新規 issue では書かない、で統一されていることが実測で確認できている)
3. 社内運用用語は「何が起きたか」が外部から読み取れる表現に置き換える。レビュー工程名・承認の流れを示す語は、結果として何が決定されたかに書き換える (例: 「〜と判定され承認のうえ closed にした」→「初回判断と独立再検証のいずれでも対応不要となったため closed にした」)。判断の根拠そのものは削除しない
4. 社内スラッシュコマンド名は、そのコマンドが実際に行った内容 (GitHub Actions の更新など) に書き換える。**本 issue の本文にも社内スラッシュコマンド名を書かない** (自分の記述で違反しながらそれを除去する、という自己矛盾を避ける)
5. `skills/` 配下の配置パスへの参照は削除し、スキル名とその参考設定であることだけ残す (スキル名自体は `hisui` の `AGENTS.md` で公開済みのため残してよい)
6. 要望者の識別は、外部ユーザーからの要望なのか開発者間の会話なのかを一般化して書く (`利用者からの要望` など)。`Reporter:` フィールドと `@voluntas` クレジットは対象外
7. 他リポジトリのファイルへの参照は、**削除せずリポジトリ名を明記して解決できる状態にする** (`shiguredo/sora-rust-sdk` の `docs/SORA_CPP_SDK.md` のように書く)。存在確認済みの公開先を指すなら、情報を消すより辿れるようにするほうが価値が高い
8. 書き換えは本文の技術的結論を変えない。判断根拠が消えてはならない (本文ごと作り直す磨き上げとは目的が違う)
